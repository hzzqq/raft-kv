# 可展示实验（experiments）

把「系统确实容错、可扩展」从**测试通过**变成**可演示、可放进作品集的证据**。

本目录是 `raftkv` 的**独立 Go 子模块**（`go.mod` + `replace raftkv => ../`），不计入父模块的测试覆盖门禁，**不会动摇已冻结的 100 分工具链**。三个实验用 `src/cluster` 的内存 labrpc 集群框架真实跑 Raft/ShardKV，注入故障（kill 副本 / 网络分区）并断言恢复，打印一条带相对时间戳的时间线。

## 运行方式

在 `experiments/` 目录下，需本机 Go 1.22 工具链：

```bash
go run . -scenario leader     # 场景 A：leader 故障切换
go run . -scenario partition  # 场景 B：网络分区脑裂（2+3 分裂）
go run . -scenario perf       # 场景 C：ShardKV 分片 vs 单组吞吐曲线
```

运行产物落在 `experiments/results/`：

| 文件 | 说明 |
| --- | --- |
| `perf_shard_scaling.json` | 场景 C 各档（1/2/3/5 组）吞吐 + 延迟分位 |
| `perf_shard_scaling.svg` | 场景 C 柱状图（白底，可直接嵌报告） |
| `scene_leader.log` | 场景 A 真实运行时间线 |
| `scene_partition.log` | 场景 B 真实运行时间线 |

控制台 `raft-kv-console` 的 **「实验与验证」Tab** 会只读托管 `results/` 目录，把上述真实产物渲染成图表与时序日志（后端 `/api/experiments/*`，已做路径穿越防护）。重新生成产物后，刷新该 Tab 即可看到最新结果。

## 场景 A · leader 故障切换

**证明**：3 副本杀 1，剩余 2 满足多数派（2/3），集群在选举超时内选出新主，且**旧任期已提交日志零丢失**。

**步骤**：起 1 组 × 3 副本 → 写 10 条热数据 → 定位 leader → `Kill()` 模拟进程崩溃 → 探测新 leader（任期递增）→ 故障后新写可读、故障前数据完整保留 → 新 leader 在新任期提交后 commit 追平旧 leader。

**真实运行结果**（1 组 × 3 副本）：

```
[t=+0.87s] 初始 leader = g0-2 | term=1 commit=12 applied=12
[t=+0.87s] kill leader g0-2（模拟进程崩溃）
[t=+1.19s] 新 leader 选出 = g0-0 | term=2（旧 term=1，+1）        ← 故障切换 ~0.32s
[t=+1.32s] ✓ 故障切换后新写可读（survivor=yes）
[t=+1.32s] ✓ 故障前已提交数据完整保留（k0=v0），旧任期日志零丢失
[t=+1.32s] ✓ 新 leader 已补齐并提交至 commit=14（≥ 旧 commit=12），日志连续无空洞
```

> 注：新 leader 刚当选时 commit 可能暂时落后旧 leader，这是 Raft「不能仅靠副本数提交旧任期条目」规则的体现；待其提交新任期首个条目后即追平（如本例 commit 12→14）。

## 场景 B · 网络分区脑裂（2+3 分裂）

**证明三条不变量**：① 多数派（3/5）继续选出新 leader 并正常读写；② 少数派（2/5）里的旧 leader 仍自认 leader、客户端也连得上它，但因拿不到 quorum 而无法提交——客户端拿到**超时错误**，绝不会拿到「写成功」；③ 愈合后少数派自动降级追平，分区期间被塞进少数派日志的未提交写被覆盖，**无脑裂双写、无已确认写丢失**。

**步骤**：起 1 组 × 5 副本 → 写热数据 → 定位 leader → `PartitionKV` 做 2+3 真网络分裂（旧 leader 落少数派）→ 断言多数派换主且可读写 → 直连少数派 leader 写被拒（不返回成功）→ 愈合后断言旧 leader 降级、ghost-write 被覆盖、所有已确认写存活。

**真实运行结果**（1 组 × 5 副本，2+3 分裂）：

```
[t=+1.00s] 分区前 leader = g0-0 | term=2 commit=8
[t=+1.00s] 网络分裂生效：少数派 [0 1]（含旧 leader）| 多数派 [2 3 4]
[t=+1.33s] ✓ 多数派选出新 leader = g0-4 | term=3（旧 term=2）
[t=+2.34s] ✓ 多数派读写正常（during-partition=ok），客户端未感知故障
[t=+2.34s] 少数派旧 leader 自述: role=Leader term=2 commit=8 leaderLease=false
[t=+5.34s] ✓ 客户端直连少数派 leader 写入被拒: err=ErrTimeout（耗时 3.0s），未拿到任何成功确认
[t=+5.34s] ✓ 少数派提交进度冻结在 commit=8，同期多数派已推进到 commit=10
[t=+5.53s] ✓ 旧 leader 已降级为 Follower、任期对齐到 term=3、applied=10（追平多数派）
[t=+5.53s] ✓ 少数派未提交的 ghost-write 已被新 leader 日志覆盖，最终状态里不存在
[t=+5.53s] ✓ 所有已确认写入全部存活（分区前 + 分区中），零丢失
```

**结论**：决定可写性的是 **quorum 而非连通性**——少数派活着也写不进，故不会脑裂双写。

## 场景 C · 分片扩展性对比曲线

**回答此前无人回答的问题**：ShardKV 把 10 个分片摊到更多 group 之后，吞吐到底涨不涨？此前 bench 只有一个孤立数字（单组、单客户端），既看不出扩展性，也无法判断瓶颈。

**方法**：对 1/2/3/5 组各跑一轮固定时长（3s）的并发读写（12 客户端），输出吞吐 + 延迟分位，落盘 JSON/SVG。

**真实运行结果**（每组 3 副本，12 并发客户端，每档 3s，内存 labrpc）：

| 组数 | 吞吐 ops/sec | 相对 1 组 | p50 ms | p95 ms | 错误 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 931.2 | 基准 | 12.5 | 26.0 | 0 |
| 2 | 1525.9 | 1.64x | 7.0 | 18.2 | 0 |
| 3 | 1968.3 | 2.11x | 4.0 | 17.0 | 0 |
| 5 | 2683.4 | 2.88x | 4.0 | 11.0 | 0 |

**结论**：分片带来有效横向扩展（5 组 = 单组的 2.88x），瓶颈成功从单个 Raft 组摊开。

## 诚实声明（重要）

- 实验使用的是 **内存 labrpc 传输**，无真实网络与磁盘。绝对值只在**同机、同参数**下可比；真正有价值的是「随 group 数变化的相对趋势」，而非某个孤立吞吐数字。
- 场景 A/B 的故障注入（kill 副本、网络分区）作用于内存集群的模拟网络层，证明的是**共识与状态机层面的正确性不变量**，而非操作系统级进程真正崩溃的恢复时序（后者由 `deploy/` 的 docker-compose + Prometheus/Grafana 在真实进程形态下观测）。
- 各场景的「✓/✗」判定来自代码内断言；日志即为真实运行输出，非编造。
